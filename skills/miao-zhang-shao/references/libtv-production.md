# LibTV 制作、剪辑与恢复

这是宿主通过当前LibTV工具自行编排的流程，不要求Canvas Agent或创作模板。先发现当次工具，再按实时契约调用；下列字段用于理解已验证路线，不替代未来的工具schema。

## 连接与项目

调用`doctor`检查身份和当前准入；连接ready只证明连接。按需求用`list_projects`定位、`create_project`新建，随后`target_project`绑定精确projectId。保留回读的项目、空间和节点身份，不用数组位置或重名推断。

完整分镜可以用`create_script_v2`保存，再`read_script_v2`核对；新版长剧本文档使用它自己的screenplay/VFS接口，不混为一类。宿主另存生成时长、预计剪辑时长、真实任务与媒体映射，便于重建。

每个新写入/生成有稳定幂等键；同一受理状态未知的任务只恢复原键、原参数和原task_id。不要把`cop_`画布写入回执当成视频任务成功。

## 角色、场景与首帧

1. 用`search_models`发现图片模型，`get_model`读取真实参数。图片默认每项一张；所需的角色、环境和各段首帧是制作资产，不额外做无请求的变体。
2. 一个双猫身份参考可同时固定白/黑英短：纯色毛、圆脸、小圆耳、短粗四肢和自然猫爪。场景参考固定石磨、工作台、灶台的相对位置、材料与光线。
3. 各段首帧通过工具连线接入这些参考。画面里先有会影响笑点的篮子、木柄、模具、空筛或碗；食物处在正确阶段，事故尚未发生。
4. 实际查看像素：猫是否多了一只、出现人手/衣服、黑猫变花猫、黄豆变花生、豆浆提前成豆腐、道具不可能接触等。发现问题先修首帧，不能直接继续花积分生成。

只有连接到项目节点的`{{Node 精确节点ID}}`引用才用于生成；提示词提到某个ID不会自动连线。使用`left`等真实引用入口或明确的首帧角色，不在params手填媒体列表或自行计算Image编号。

## H3生成路线与参数

默认`search_models`查MiniMax H3，再`get_model`核对精确模型标识；H3 Max是另一个模型。已经验证的H3单首帧路线使用：

```text
intent = generate
startFrameNode = 已验收首帧的真实节点ID
model = get_model返回的精确H3标识
params = 当前契约允许的创作字段
```

当前系列约定768P生成、720×1280交付；只有实时契约仍支持时才沿用。单首帧模式的比例字段可能是`ratio_auto=adaptive`，不能照搬文生视频的`ratio_t2v`。时长选常规6–7秒、复杂8–9秒，count=1；使用用户明确覆盖值时遵循其要求。

指定模型不可用、所需能力不支持或工具要求积分确认时，说明具体阻塞并按工具流程处理；不自行换模型、升级档位或重复扣费重试。用户已授权的常规生成不额外增加确认步骤。

若模型的自动模式不能覆盖两张参考图输入，不删掉角色参考后偷偷改成纯文生。可将多张角色/环境参考先用于定帧，再用该定帧作视频首帧。单首帧生成与多图参考的能力不是同一个判断。

`create_node(run=true)`等异步入口返回实际task_id后，用`task_status`回读。若`generate_video`同一次调用正在等待结果，只等原调用/原exec cell结束，不并行查任务或重复生成。只在它结束且明确要求恢复时按原任务查询。

## 提示词与食物状态

提示词保持短而明确：当前首帧身份与空间、当前食物状态、一个动作单元、后果与反应、必要切换、声音。不要给每个镜头重复整道菜流程。

制豆腐示例：

| 当前段 | 可见起点 | 应到达的结果 | 不能提前出现 |
|---|---|---|---|
| 摘豆剥荚 | 地上大豆植株与成熟扁豆荚 | 圆黄豆入筛 | 地下花生、网纹花生壳 |
| 浸泡 | 干豆与水 | 明确时间跳切后的泡涨豆 | 豆腐块 |
| 磨浆 | 泡豆进入磨眼 | 豆浆流入接浆容器 | 整粒豆从出浆口原样掉出、压好的豆腐 |
| 过滤 | 生豆浆和滤布 | 液体与豆渣分开 | 豆腐方块 |
| 点卤 | 煮熟并适当静置的豆浆 | 柔软絮状豆花 | 已切好的方块豆腐 |
| 压制开模 | 豆花入布和木模 | 一整块成形豆腐 | 直接跳到炒好的成菜 |

这张表用于审阅和阶段边界；不要把整张表塞进每个模型提示词。若产物仅在尾部跳到错误状态，先找可保留完整动作的裁剪点；不够用才考虑最小范围重拍。

## 剪辑与音频

从真实输出更新时长、尺寸、帧率、音轨与源区间。生成请求10秒不保证容器恰好10秒；不要凭请求值推断文件长度。分别保存源秒数与输出秒数，不能把剪辑结束点缩短当作隐式变速。

正常路线是`export_readiness`→`export_video`→`export_status`/`task_status`。开始前确认所有源可用，使用新导出专用稳定键。已有任务状态未知时查原任务，不重发。

保留现场声，轻快纯器乐留出拟音空间。音频按真实长度和时间线对齐，完整试听与电平分析分开记录。原生负decibel、正增益和全局volume的语义以当次工具说明为准，不凭字段名猜测。

## 两类已遇到的导出问题

- `EXPORT_SOURCE_DURATION_REQUIRED`：音频回执缺少可验证时长时，先检查真实文件/媒体信息，不把请求的120秒伪写成源时长。如果原生路线仍不能接入，先合成视频现场声，再在本地混音；或对通过交付检查的全部源素材一次本地合成。
- 原生Task成功，但`mediaPersistence`显示missing，交付返回`DELIVERY_OUTPUT_REQUIRED`或`DELIVERY_SOURCE_CHANGED`：TaskResult临时投影的URL不是持久绑定。可按真实Resource身份核对，仍不能交付时不要强填URL/资源或直接下载绕过。对已绑定的源镜头与配乐重新取得合法交付清单，本地合成后回传最终文件。

本地回退保留相同镜头顺序和真实裁剪区间，保存命令/工程与hash。只使用清单准许的文件；水印/会员选择不明确时按工具要求取得用户决定，不自行绕过。不要把本地回退描述成LibTV原生合成成功。

## 文件保存、上传与最终证据

`prepare_project_delivery`只准备清单。逐项保存或核对已从同一URL取得的实际字节、大小和hash；媒体仍要完整解码与看画面。manifest或成功链接不等于本地文件已经存在。

回传最终片：

1. 成片完成并验收后，按真实文件名、大小和需要的hash申请`upload_ticket`，检查`originAllowed`与各part的来源。
2. 用实际文件字节和票据规定的method/headers上传parts，保存每part回执。不要把文件路径当作已上传。
3. `upload_complete`使用原path与uploadId；响应未知只恢复同一次上传，不新开票据重复上传。
4. 将返回的file_ref原样传给`upload_media`，使用稳定键和原参数。review_pending沿原流程恢复；review_rejected停止盲重试。只有completed才说明挂载完成。
5. 回读最终节点、Resource、真实持久化URL、分辨率、时长和音轨，再展示成片卡。

**签名403诊断：**遵循票据的具体签名约定，不通用地删请求头。已遇到的OSS V1票据签了空Content-Type，Python urllib却自动补form类型，导致403；核对错误后显式保留空Content-Type，同一part上传成功。其他票据若要求Content-Type则必须照做。不要因这个错误反复OAuth或新建上传。

签名URL、file_ref、认证材料不写入skill或公开交付文档；必要的临时凭据限制在任务临时文件，成功后清理。保留非秘密的项目/节点/Task/Resource和上传回执供恢复。
